# 数值与结局设计

这份文档记录的是**方法论**，不是格式。格式看 [story-format.md](story-format.md)。

核心问题只有一句话：**你拍的阈值，和玩家实际能涨到的数值，往往不是一回事。**

`npm run validate` 会把可达状态全走一遍，把这件事算清楚。下面是踩过的三个真实案例。

---

## 案例一：max 设成 100，但全流程只能涨到 40

第一版数值条这样写的：

```js
{ key: '圣宠', init: 0, min: 0, max: 100 }
```

看起来很正常。但穷举后发现，全流程所有路径加起来，`圣宠` 最高只能到 **20**。

结果：进度条永远只填 20%，玩家玩了半小时，觉得「怎么一点没涨」——**实际观感是系统坏了**。

### 正确做法

`max` 不是「100 分满分」这种直觉数字，而是**真实可达上限**：

```js
{ key: '圣宠', init: 0, min: 0, max: 25 }   // 实测上限 20，留点余量
```

先跑校验，看输出里的数值范围，再回来定 `max`。

```
✓ 数值  圣宠 4~20  心计 15~35  声望 0~40  银两 130~260
              ↑ 照着这个定 max
```

## 案例二：阈值拍高了，结局根本够不着

第一版结局条件是：

```js
require: '圣宠>=55 && 心计>=55'      // 想表达「圣宠和心计都到一半以上」
```

但实测上限是 `圣宠 20 / 心计 35`。于是：

```
各结局可达路径数:
   冷宫     432
   （其余三个全是 0）
```

**432 条路径，全部只能走兜底结局。** 三个精心设计的分支等于不存在。

校验器直接报：

```
✗ 结局「凤仪天下」的条件永远满足不了——数值涨不到，或者需要的标记拿不到
```

### 正确做法

阈值要从**实际可达范围**倒推，不是从「满分」倒推：

| 结局 | 设计意图 | 拍的阈值 |
|---|---|---|
| 凤仪天下 | 最难，少数路径 | `圣宠>=17 && 心计>=28`（占 6% 路径） |
| 长乐无极 | 中等 | `声望>=26`（占 14%） |
| 雪夜出宫 | 隐藏线 | `has('玉佩') && 银两>=150`（占 16%） |
| 冷宫 | 兜底 | 无条件 |

最终分布：

```
凤仪天下 40 条 / 长乐无极 92 条 / 雪夜出宫 108 条 / 冷宫 432 条
```

> 「最难」的结局占 6% 路径是健康的：够稀有，但不至于只有一条路能拿到。

## 案例三：互斥资源陷阱（最隐蔽）

出宫结局要求：

```js
require: "has('玉佩') && 银两>=250"
```

看起来很合理。但剧情里只有两处给资源，而且是**二选一**：

```js
choices: [
  { text: '收下玉佩', effect: { flags: ['玉佩'] } },              // 拿玉
  { text: '把玉还回去，摸走母亲的私房钱', effect: { 银两: 120 } }, // 拿钱
]
```

**玉佩和银两互斥 → 这个结局在数学上永远不可能达成。**

这种 bug 人眼极难发现，因为它不是「写错」，而是两个正确的东西组合起来错了。穷举路径一跑就现形。

### 正确做法

- 要么让资源能同时获得（补一条银两来源）
- 要么降低阈值到单条路径就能满足（`银两>=150`）
- 要么把条件改成只依赖标记（`has('玉佩')`）

---

## 设计流程

**不要**先写数值再写完剧情再定阈值。正确顺序：

```
1. 写完剧情骨架（节点 + 分支，数值先随便给）
2. 跑 npm run validate，看输出里的「数值 X~Y」真实范围
3. 用真实范围倒推 max 和结局阈值
4. 再跑一遍，确认每个结局的路径数都 > 0
5. 觉得某个结局太容易/太难，微调阈值，重复第 4 步
```

这是**一分钟一轮**的循环，比凭感觉拍数字可靠得多。

## 读校验器输出

```
▶ zhiwei  知微
  ✓ 结构  55 个节点 / 6 个结局
  ✓ 路径  200000+ 条通关路径
  ✓ 状态  400000 个去重状态
  ✓ 结局  凤仪天下(13k)  长乐无极(56k)  雪夜出宫(27k)  双生(36k)  玉碎(18k)  冷宫(66k)
  ✓ 数值  圣宠 2~21  心计 33~60  声望 4~60  银两 40~260
  → 通过
```

| 行 | 怎么用 |
|---|---|
| 结局 `xxx(N)` | **N 必须 > 0**。为 0 说明这个结局做了等于没做 |
| 数值 `A~B` | 用 B 定 `max`，用 A~B 的区间定阈值 |
| 路径总数 | 太少（<20）说明分支不够；太多说明分支没有收束 |
| 状态数 | 分支多时路径数会失真，状态数才是「到底有多少种局面」 |

警告也要看：

```
! 选项永远点不到：「c5_1」第 1 个（条件 声望>=26）
```

这是在说：你设计的这条选项，**在所有可达状态里没有任何一个能满足它**。

## 其他经验

### 每个决策节点必须有兜底

```js
choices: [
  { text: '需要条件的选项', next: 'x', require: '声望>=30' },
  { text: '无条件兜底',     next: 'y' },        // ← 必须有
]
```

全锁死的节点 = 玩家卡死。校验器会对这种情况直接报错。

### 条件锁要显示，不要隐藏

条件不满足时**显示但置灰**，配一句 `hint`：

```js
hint: '需 声望 26'
```

让玩家看见自己错过了什么，比藏起来更能勾起重玩的欲望。

### 数值量级

单个数值全流程总涨幅控制在 **20~40** 左右比较好：

- 太小（个位数）：每次 +1 没有反馈感
- 太大（几百）：玩家记不住，也无从判断好坏

### 选项数量

单节点 **2~4 个**最佳。超过 6 个，手机上要滚动才能看完，决策疲劳。

### 节点长度

**120~220 字**。超过 250 字手机上要滚动，节奏就散了。

---

## 一句话总结

> 数值系统不是写出来的，是**量出来的**。
> 每加一章剧情，都要重新跑一遍 `npm run validate`，看着真实范围去调阈值。
